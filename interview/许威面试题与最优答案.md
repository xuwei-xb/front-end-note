## 一、项目深度追问

### Q1. 腾讯工作流平台：你说重构了画布渲染逻辑，优化了海量流程节点渲染性能，具体怎么做的？

**面试官问法：** "简历上提到重构画布渲染逻辑、优化海量节点渲染性能，能详细讲讲吗？"

**最优回答思路（STAR）：**

**背景：** 工作流平台基于 ReactFlow 构建，当画布上节点数量超过 200+ 时，拖拽、缩放出现明显卡顿，FPS 掉到 15 以下。

**分析：** 用 Chrome DevTools Performance 面板分析，发现瓶颈在三处：
1. 每次画布变化触发全量节点 re-render，React Diff 开销大
2. 连线 SVG 路径计算同步阻塞主线程
3. 节点内部组件未做 memo，父级 render 导致子级连锁更新

**行动：**
1. **节点虚拟化渲染**：只渲染视口可见区域内的节点（视口裁剪计算 + 虚拟列表），不可见节点用占位 DOM，减少 DOM 数量
2. **React.memo + 精确依赖**：对节点组件套 `React.memo`，自定义 `arePropsEqual` 只比较关键 prop（position、data、selected），避免无关字段变更触发重渲染
3. **连线计算异步化**：将 SVG 路径计算放到 `requestIdleCallback` 或 Web Worker，主线程只负责最终绘制
4. **节点分层渲染**：将节点分为"选中态层""连线层""普通节点层"，z-index 分层，减少重绘范围
5. **批量状态更新**：用 `unstable_batchedUpdates` 或 React 18 自动批处理，合并高频拖拽事件触发的状态更新

**结果：** 节点数 500+ 时 FPS 从 15 提升到 50+，拖拽延迟从 200ms 降到 30ms 以内。

**追问准备：**
- "ReactFlow 的连线层级遮挡问题怎么修复的？" → 调整 SVG `<g>` 的 z-index 层级，将连线放在节点 DOM 之下，选中节点单独提升层级
- "虚拟化怎么判断节点是否在视口内？" → 通过 ReactFlow 的 `viewport` 和 `transform` 计算节点的实际屏幕坐标，与视口边界做交集判断

### Q2. 腾讯混元官网：对接大模型 API，NestJS 封装请求中间层，具体怎么设计的？

**面试官问法：** "文生图、语音转文字这些 AI 能力的前后端交互链路是怎么打通的？"

**最优回答思路：**

**架构设计：**

```
前端组件 → NestJS 中间层(API网关) → 大模型API(腾讯混元/第三方)
                ↓
          Redis(缓存/限流)
                ↓
          MongoDB(对话日志)
```

**NestJS 中间层职责：**
1. **统一鉴权**：前端请求带 JWT Token，NestJS Guard 统一校验，再转发给大模型 API
2. **请求封装**：不同大模型 API 参数格式不同（文生图 vs 语音转文字 vs 对话），NestJS 统一封装适配层，前端只调一个标准化接口
3. **流式转发**：大模型流式响应（SSE）通过 NestJS 透传给前端，用 `@Sse()` 装饰器实现
4. **缓存策略**：相同 prompt 的请求用 Redis 缓存（设置 TTL），避免重复调用大模型
5. **日志记录**：每次请求的 prompt、模型参数、响应耗时写入 MongoDB，用于后续分析和成本追踪
6. **限流降级**：基于 Redis 计数器实现令牌桶限流，防止恶意刷接口；大模型超时自动降级返回缓存结果

**前端组件封装：**
- 封装 `useAIChat` Hook：管理对话上下文、流式接收、错误重试
- 封装 `AIImageGen` 组件：文生图交互（输入 prompt → loading → 展示结果 → 下载）
- 封装 `AIVoiceToText` 组件：录音 → 上传 → 返回文字
- 统一异常处理：超时、限流、模型异常都有对应的 UI 反馈

**追问准备：**
- "大模型流式输出前端怎么接收的？" → 使用 `fetch` + `ReadableStream` 或 EventSource (SSE)，逐 chunk 解析 `data:` 字段，增量更新 UI
- "3D 模型生成模块怎么做的？" → 前端用 Three.js 预览模型，后端调大模型生成 `.glb` 文件，前端通过 URL 加载并支持下载

### Q3. 低代码平台：组件引擎是怎么设计的？可拖拽组件的渲染机制是什么？

**面试官问法：** "低代码平台的组件引擎核心架构是什么样的？"

**最优回答思路：**

**核心架构分三层：**

```
┌─────────────────────────────────┐
│  渲染层 - 根据 schema 树递归渲染组件  │
├─────────────────────────────────┤
│  逻辑层 - 事件绑定 / 数据流 / 表达式引擎 │
├─────────────────────────────────┤
│  物料层 - 组件注册 / 属性配置面板 / 拖拽  │
└─────────────────────────────────┘
```

**1. 物料层（组件注册）：**
- 每个低代码组件注册时声明 `schema`：组件类型、可配置属性、默认值、属性面板配置
- 组件发布到 NPM 私有仓库，主应用通过动态 import 按需加载
- 拖拽使用 `dnd-kit` 或自研拖拽引擎，拖入画布时生成一个组件实例节点

**2. 逻辑层（数据与事件）：**
- **表达式引擎**：组件属性可以绑定表达式（如 `{{dataSource.list.length}}`），用 `new Function` 或 AST 解析执行
- **事件系统**：组件间通过发布订阅通信，事件配置存在 schema 的 `events` 字段
- **数据源管理**：统一管理 API 请求，组件通过 `dataBinding` 绑定数据源

**3. 渲染层（Schema → DOM）：**
- 画布维护一棵 JSON Schema 树，每个节点描述一个组件实例
- 递归遍历 schema 树，根据 `componentType` 动态渲染对应组件
- 用 `React.memo` 优化：只有 schema 节点变化时才重渲染对应子树
- 属性面板修改 → 更新 schema 节点 → 触发对应组件 re-render

**追问准备：**
- "schema 怎么持久化的？" → JSON 序列化存 MongoDB，支持版本管理和回滚
- "组件间怎么通信？" → 通过全局状态管理（Context / Zustand），或事件总线发布订阅

### Q4. 微前端 qiankun：主子应用通信怎么做的？样式隔离呢？

**面试官问法：** "qiankun 微前端架构下，主应用和子应用怎么通信？样式冲突怎么解决？"

**最优回答思路：**

**主子应用通信（三种方案）：**

1. **Actions 通信（qiankun 官方方案）**
   - 主应用 `initGlobalState` 创建全局状态
   - 子应用 `onGlobalStateChange` 监听、`setGlobalState` 修改
   - 适合简单场景，状态共享

2. **自定义事件通信**
   - 用 `CustomEvent` / `window.dispatchEvent` 做事件通信
   - 主应用监听子应用触发的事件，反之亦然
   - 适合一次性事件通知（如登录状态变更）

3. **共享数据层**
   - 主应用挂载一个全局 Store 到 `window.__POWERED_BY_QIANKUN__`
   - 子应用通过 window 访问共享数据
   - 项目中实际用的方案：主应用管理用户信息、权限数据，子应用通过 `props` 注入获取

**样式隔离：**

1. **qiankun `sandbox` 配置**
   - `experimentalStyleIsolation: true`：给子应用所有样式加 `div[data-qiankun]` 前缀
   - `strictStyleIsolation: true`：用 Shadow DOM 隔离（但会影响弹窗、全局事件等）

2. **CSS Modules / Scoped CSS**
   - 子应用内部用 CSS Modules 或 Vue `<style scoped>`
   - 避免全局样式名冲突

3. **约定命名前缀**
   - 不同子应用用不同 CSS 类名前缀（如 `app-a-header`、`app-b-header`）

4. **实际项目做法**
   - 关闭 strictStyleIsolation（Shadow DOM 兼容性问题太多）
   - 用 `experimentalStyleIsolation` + CSS Modules + 前端规范约定
   - Element UI / Ant Design 用按需加载 + CSS Modules 避免全局污染

**追问准备：**
- "子应用怎么按需加载？" → 主应用配置 `activeRule`，路由匹配时才加载子应用资源
- "子应用独立部署怎么做？" → 每个子应用独立构建部署，主应用通过 `entry` 配置加载子应用 HTML

### Q5. React Native 跨端：从零搭建项目，Android/iOS 统一渲染逻辑怎么保证的？

**面试官问法：** "你说从零搭建 React Native 跨端项目，Android 和 iOS 的渲染差异怎么处理的？"

**最优回答思路：**

**核心原则：业务逻辑 100% 共享，平台差异封装到适配层。**

**架构分层：**

```
┌──────────────────────────────────┐
│  业务组件层（跨平台共享，不感知平台差异）    │
├──────────────────────────────────┤
│  平台适配层（Platform.select / Native模块） │
├──────────────────────────────────┤
│  RN 原生层（Android: Java/Kotlin, iOS: Swift）│
└──────────────────────────────────┘
```

**具体做法：**

1. **样式统一**
   - 使用 `StyleSheet.create` 而非内联样式
   - 尺寸用 `Dimensions.get('window')` 动态适配，不硬编码
   - 字体大小、间距用统一 Design Token，通过 `Platform.select` 做微调

2. **平台差异封装**
   - 透明状态栏、安全区域：用 `SafeAreaView` + `Platform.select` 统一处理
   - 导航：用 React Navigation，配置统一路由栈
   - 原生模块：需要调原生 API 的功能（如相机、推送）封装成统一 JS 接口，内部判断平台

3. **条件编译**
   - 文件级：`Component.ios.tsx` / `Component.android.tsx`，Metro 自动加载对应平台文件
   - 代码级：`Platform.OS === 'ios'` 做条件分支

4. **Expo 集成**
   - 用 Expo 简化原生模块管理，`expo-camera`、`expo-image-picker` 等跨平台 API
   - 需要 eject 时用 `npx expo prebuild` 生成原生代码

**追问准备：**
- "RN 和原生怎么通信？" → Bridge（旧架构）/ JSI（新架构），通过 NativeModules 调用原生方法
- "RN 性能怎么优化？" → 列表用 FlatList（虚拟化）、图片用 react-native-fast-image、动画用 Animated + useNativeDriver

### Q6. Kerala Lottery 海外彩票平台：NestJS 怎么封装第三方游戏数据接口的？

**面试官问法：** "第三方游戏数据接口怎么统一处理的？"

**最优回答思路：**

**问题：** 多个第三方游戏供应商 API 格式各异（Kerala、PowerBall、MegaMillions），前端直接对接需要适配多套数据结构。

**解决方案：**

1. **适配器模式**
   - 定义统一的 `GameService` 接口：`getLotteryResult()`、`getGameList()`、`placeBet()`
   - 每个供应商实现一个 Adapter：`KeralaAdapter`、`PowerBallAdapter`、`MegaMillionsAdapter`
   - NestJS Provider 根据请求参数动态选择 Adapter

2. **统一数据模型**
   - 定义统一的 DTO（`LotteryResultDTO`、`BetDTO`），所有 Adapter 将第三方数据转换为统一格式
   - 前端只对接标准化接口，无需感知供应商差异

3. **请求封装**
   - 每个 Adapter 内部用 `HttpService`（Axios）封装各自的鉴权方式（有的用 API Key，有的用 OAuth）
   - 统一超时配置、重试策略、错误格式化

4. **缓存策略**
   - 开奖结果用 Redis 缓存（TTL 5 分钟），减少第三方调用
   - 历史数据缓存时间更长

## 二、前端核心技术原理

### Q7. Vue 2 和 Vue 3 的响应式原理有什么区别？

**面试官问法：** "简历上写熟悉 Vue 响应式原理，说说 Vue 2 和 Vue 3 响应式的区别？"

**最优回答思路：**

| 维度 | Vue 2 | Vue 3 |
|------|-------|-------|
| 核心机制 | `Object.defineProperty` | `Proxy` |
| 监听范围 | 只能监听已声明属性 | 新增/删除属性自动响应 |
| 数组监听 | 需重写 7 个变异方法 | 原生支持 |
| 性能 | 初始化递归遍历所有属性 | 惰性响应（访问时才转换） |
| 兼容性 | IE9+ | 不支持 IE |

**Vue 2 原理：**
- `Object.defineProperty` 对 data 的每个属性定义 `get`/`set`
- `get` 时收集依赖（Dep + Watcher）
- `set` 时通知依赖更新
- 缺陷：新增属性需 `Vue.set()`；数组需重写变异方法；深层对象初始化递归性能差

**Vue 3 原理：**
- `reactive()`：用 `Proxy` 代理整个对象，`get` 时用 `track()` 收集依赖，`set` 时用 `trigger()` 触发更新
- `ref()`：用 `RefImpl` 类包装原始值，`.value` 的 get/set 触发响应
- 惰性收集：只有被 `effect` 读取的属性才建立依赖关系，未访问的属性不触发更新
- 性能优势：初始化不递归遍历；Proxy 是引擎层面拦截，比 defineProperty 快

**加分点：**
- 提到 Vue 3 的 `effectScope` 管理 effect 生命周期
- 提到 `shallowReactive` / `shallowRef` 只代理第一层
- 提到 `markRaw` 跳过响应式转换

### Q8. React Hooks 性能优化你做了哪些？

**面试官问法：** "简历上提到主导 React 项目性能优化，具体做了哪些？"

**最优回答思路：**

**分场景优化策略：**

1. **避免不必要的 re-render**
   - `React.memo`：包裹子组件，props 不变时跳过渲染
   - `useMemo`：缓存计算结果（如复杂的列表过滤、排序）
   - `useCallback`：缓存事件处理函数引用，避免传递新函数引用给 memo 子组件
   - **关键认知**：`useMemo`/`useCallback` 本身有开销，不要滥用。只在传递给 `React.memo` 子组件或依赖数组中使用才有意义

2. **状态拆分与下移**
   - 把频繁变化的状态下移到叶子组件，避免高层组件 re-render
   - 大表单用 `useReducer` 替代多个 `useState`，减少状态碎片化

3. **列表虚拟化**
   - 大列表用 `react-window` 或 `react-virtualized`，只渲染可见行
   - 工作流平台 500+ 节点就是这个方案

4. **批量更新**
   - React 18 自动批处理：事件回调、setTimeout、Promise 中的多次 setState 会合并
   - 紧急更新优先：`useTransition` / `startTransition` 标记非紧急更新，避免阻塞用户交互

5. **代码分割**
   - `React.lazy` + `Suspense` 路由级懒加载
   - `import()` 动态导入重组件（如 3D 预览、图表）

6. **并发渲染（React 18）**
   - `useDeferredValue`：延迟渲染搜索结果，输入框不卡
   - `useTransition`：将昂贵的状态更新标记为过渡，保持 UI 响应

**追问准备：**
- "useMemo 和 useCallback 有什么区别？" → useMemo 缓存值，useCallback 缓存函数引用；useCallback(fn, deps) 等价于 useMemo(() => fn, deps)
- "什么时候不该用 useMemo？" → 缓存值比计算本身还简单时（如简单字符串拼接），依赖数组频繁变化时

### Q9. Vue 和 React 的 Diff 算法有什么区别？

**面试官问法：** "你说熟悉 Diff 算法，Vue 和 React 的 Diff 有什么不同？"

**最优回答思路：**

**共同基础：** 都基于同层比较、Type 标识、Key 优化（同级比较，不跨层移动）。

**Vue 2 Diff（双端对比）：**
- 使用**双端算法**：头头、尾尾、头尾、尾头四种对比
- 先处理首尾相同的新旧节点（最优路径），再处理中间乱序部分
- 乱序部分用旧节点 key → index 的 Map 查找

**Vue 3 Diff（最长递增子序列）：**
- 头部预检：从头跳过相同节点
- 尾部预检：从尾跳过相同节点
- 中间部分：用**最长递增子序列（LIS）**算法找到不需要移动的节点
- 只有不在 LIS 中的节点才需要 DOM 移动，减少真实 DOM 操作次数

**React Diff（单向从左到右）：**
- 从左到右逐个比较，用 key 匹配旧节点
- 遇到 key 不在旧集合中 → 新增
- 遇到旧节点 key 不在新集合中 → 删除
- 移动节点时直接移动，不找最优移动方案（不如 Vue 3 的 LIS 聪明）

**核心差异总结：**
- Vue 2 双端对比 > React 单向遍历
- Vue 3 LIS 算法 > Vue 2 双端对比 > React 单向遍历
- React 的 Fiber 架构使得 Diff 可中断恢复，Vue 的 Diff 是同步不可中断的

### Q10. TypeScript 中 type 和 interface 的区别？什么场景用哪个？

**最优回答思路：**

| 维度 | `interface` | `type` |
|------|------------|--------|
| 扩展方式 | `extends` 继承 | `&` 交叉类型 |
| 声明合并 | 同名自动合并 | 不允许重复定义 |
| 描述范围 | 对象/类 | 对象/原始值/元组/联合/映射 |
| 计算 | 不支持 | 支持条件类型、映射类型 |

**实际选择：**
- **对象/类形状** → 优先 `interface`（支持声明合并、扩展更直观）
- **联合类型/交叉类型/工具类型** → 必须 `type`
- **API 响应/DTO** → `interface`（可被工具自动生成，如 Swagger Codegen）
- **组件 Props** → `interface`（React 官方风格指南推荐）

### Q11. WebSocket 实时通讯怎么实现的？心跳保活怎么做的？

**面试官问法：** "你在低代码平台做了 WebSocket 实时通讯，具体怎么实现的？"

**最优回答思路：**

**封装 WebSocket 管理类：**

1. **连接管理**
   - `new WebSocket(url)` 建立连接
   - 监听 `onopen`/`onmessage`/`onclose`/`onerror`
   - 连接状态机：connecting → connected → disconnecting → disconnected

2. **心跳保活**
   - 前端每 30 秒发送 `{"type": "ping"}`
   - 服务端响应 `{"type": "pong"}`
   - 超过 3 次未收到 pong，判定连接断开，触发重连

3. **断线重连**
   - 指数退避重连：1s → 2s → 4s → 8s → 最大 30s
   - 重连次数上限（如 10 次），超过后提示用户手动重连
   - 重连时恢复订阅的频道

4. **消息分发**
   - 消息按 `type` 字段路由到不同的处理函数
   - 支持频道订阅/取消订阅（`subscribe`/`unsubscribe`）

5. **多端协同场景**
   - 在线会议画布协同：用户操作（鼠标位置、绘制轨迹）通过 WebSocket 实时广播
   - 全局消息推送：服务端推送通知，前端弹出 Toast

**追问准备：**
- "WebSocket 和 SSE 怎么选？" → 双向通信选 WebSocket，服务端单向推送选 SSE（更轻量，自动重连）
- "大量消息怎么防止前端处理过慢？" → 消息队列缓冲 + requestAnimationFrame 批量处理

**requestAnimationFrame 和requestIdleCallback  的区别**
> requestAnimationFrame	下一帧渲染之前	高优先级（与屏幕刷新同步）	动画/视觉更新
> requestIdleCallback	浏览器空闲时	低优先级（与屏幕刷新不同步）	后台任务/优化

## 三、AI 与大模型工程

### Q12. 为什么选 LangGraph 而不是直接用 LangChain？

**面试官问法：** "你的 AI 工作流用了 LangGraph，为什么不直接用 LangChain？"

**最优回答思路：**

**LangChain 的局限：**
- `Chain` 是线性的，每次调用从头跑到尾，不支持循环、条件分支
- 状态管理弱：多步骤间的中间状态传递靠手动拼接
- 无法实现 Agent 的"思考→执行→观察→再思考"循环

**LangGraph 的优势：**
1. **图结构编排**：把工作流定义为有向图（节点 + 边），支持条件分支、循环、并行
2. **State 管理**：全局 `State` 对象在节点间流转，每个节点读写 State，无需手动传递
3. **Agent 循环**：原生支持 ReAct 模式（Reason → Act → Observe 循环），Agent 可以多轮调用工具
4. **Human-in-the-loop**：支持在特定节点暂停，等待人工确认后继续执行
5. **持久化**：支持 checkpoint，工作流中断后可恢复
6. **流式输出**：每个节点的输出可以流式传输到前端

**实际项目用法：**
- 定义 `State`（对话历史、当前步骤、执行结果）
- 每个节点是一个函数：`classifyIntent`（意图分类）→ `selectAgent`（选择 Agent）→ `executeTask`（执行任务）→ `formatResult`（格式化结果）
- 条件边：根据 `classifyIntent` 的结果路由到不同 Agent 节点
- 串行/并行：多 Agent 任务可以串行（依赖前一步结果）或并行（独立任务同时执行）

### Q13. AI Agent 调度逻辑怎么设计的？如何处理执行失败？

**面试官问法：** "多步骤 AI 工作流的 Agent 调度是怎么设计的？"

**最优回答思路：**

**调度架构：**

```
用户输入 → 意图识别 → 任务拆解 → Agent调度 → 结果汇总 → 返回
                          ↑          ↓
                          └── 失败重试 ┘
```

**调度设计：**

1. **任务拆解**：大模型根据用户输入拆分为多个子任务，每个子任务分配给对应 Agent
2. **依赖分析**：分析子任务间的依赖关系，生成 DAG（有向无环图）
3. **调度执行**：
   - 无依赖的子任务并行执行
   - 有依赖的子任务串行执行
   - 每个 Agent 有独立的 `systemPrompt` 和 `tools`
4. **结果汇总**：所有子任务完成后，汇总结果返回给用户

**失败处理策略：**

1. **重试机制**：Agent 执行失败自动重试（默认 3 次），每次重试把错误信息附加到 prompt 中，让模型自我修正
2. **降级策略**：重试失败后，降级到更简单的模型或规则引擎处理
3. **超时控制**：每个 Agent 设置超时时间（如 30s），超时后中断并返回降级结果
4. **人工介入**：关键步骤失败时，通过 LangGraph 的 `interrupt` 暂停工作流，通知人工处理

**追问准备：**
- "Agent 的工具调用怎么实现？" → 每个工具定义为 `function` schema，通过 `function calling` 让模型选择调用
- "怎么控制 Agent 的成本？" → 记录每次调用的 token 数，设置预算上限，超过预算提前终止

### Q14. 大模型流式输出前端怎么处理？SSE 和 WebSocket 怎么选？

**最优回答思路：**

**前端接收流式输出的两种方式：**

**方式一：SSE（EventSource）**
```javascript
const eventSource = new EventSource('/api/chat/stream');
eventSource.onmessage = (e) => {
  const chunk = JSON.parse(e.data);
  setMessages(prev => updateLastMessage(prev, chunk.content));
};
eventSource.onerror = () => eventSource.close();
```
- 优点：原生 API，自动重连，轻量
- 缺点：只支持 GET（实际通过 URL 传参），单向通信

**方式二：fetch + ReadableStream（推荐）**
```javascript
const response = await fetch('/api/chat', {
  method: 'POST',
  body: JSON.stringify({ messages }),
});
const reader = response.body.getReader();
const decoder = new TextDecoder();
while (true) {
  const { done, value } = await reader.read();
  if (done) break;
  const text = decoder.decode(value);
  // 解析 SSE 格式 data: {...}
  parseSSEChunk(text).forEach(chunk => {
    setMessages(prev => appendToLast(prev, chunk.content));
  });
}
```
- 优点：支持 POST 请求体、灵活控制、支持自定义 header
- 缺点：需要手动解析 SSE 格式、手动处理重连

**选择标准：**
- 大模型对话流式输出 → **fetch + ReadableStream**（需要 POST body 传 messages）
- 服务端单向推送通知 → **SSE**（简单轻量）
- 双向实时通信（如协同编辑）→ **WebSocket**

**追问准备：**
- "流式输出中 UI 频繁更新怎么优化？" → 用 `useRef` 存当前 chunk，`requestAnimationFrame` 批量 flush 到 state，避免每个 token 都触发 re-render
- "Markdown 流式渲染怎么做？" → 边接收边用 `react-markdown` 解析，用 `remark-gfm` 处理表格/代码块

### Q15. LangGraph 的 State 在节点间怎么流转的？前端怎么可视化配置？

**最优回答思路：**

**State 流转机制：**
- LangGraph 的 `State` 是一个 TypedDict，每个节点可以读取和更新 State
- 节点返回的对象会自动合并到 State 中（支持覆盖或追加）
- `Annotated[list, operator.add]`：标记列表字段为追加模式，多个节点的输出自动累加

**前端可视化配置流程：**
1. **画布编排**：用户在 ReactFlow 画布上拖拽节点（Agent、工具、条件判断），连线定义执行顺序
2. **节点配置**：每个节点弹出属性面板，配置 systemPrompt、tools、模型参数
3. **条件边配置**：连线可以配置条件表达式（如 `state.intent === 'code'`），决定路由方向
4. **Schema 生成**：画布配置导出为 JSON Schema，传给 NestJS 后端
5. **后端编译**：NestJS 接收 Schema，动态构建 LangGraph 图结构并执行
6. **实时预览**：执行过程中每个节点的状态实时推送到前端画布，高亮当前执行节点

### Q16. UniApp 和 Taro 的优缺点对比？你怎么选型？

**面试官问法：** "你同时用过 UniApp 和 Taro，两个框架怎么选？"

### Q17. 跨端开发中遇到的最大坑是什么？怎么解决的？

**最优回答思路：**

**坑一：各平台 API 差异**
- 问题：同一个功能在不同小程序平台的 API 名称、参数不同
- 解决：封装统一 API 层，内部用条件编译 `#ifdef` 分平台调用

**坑二：样式渲染差异**
- 问题：H5 的 Flex 布局在小程序中表现不一致，`position: fixed` 在 iOS WebView 中异常
- 解决：用 `rpx` 替代 `px`；复杂布局降级为 `float` 或 `table`；用 `uni.createSelectorQuery` 获取实际渲染尺寸做动态适配

**坑三：第三方 SDK 接入**
- 问题：法大大合同签署、腾讯身份证识别、TP-Link 摄像头等 SDK 只提供原生 SDK 或小程序 SDK，跨端方案不兼容
- 解决：写 **原生插件** 封装 SDK，通过 UniApp 的 `nativePlugin` 机制调用；小程序端用条件编译加载小程序版 SDK；前端统一接口调用，不感知底层差异

**坑四：App 冷启动白屏**
- 问题：WebView 加载 H5 资源慢，冷启动白屏 2-3 秒
- 解决：首屏资源预置到本地（App 打包时包含）；用 `nvue` 做启动页；预加载下一页资源

### Q23. 你做过最复杂的一次性能优化是什么？

**最优回答思路（结合工作流平台）：**

**场景：** 工作流平台画布节点 500+ 时严重卡顿，FPS 15 以下，用户无法操作。

**排查过程：**
1. Chrome Performance 录制：发现每帧 Scripting 占 80%+，Rendering 占 15%
2. React DevTools Profiler：发现节点组件全量 re-render，即使只拖动了一个节点
3. Memory 快照：发现 SVG 连线对象未释放，内存持续增长

**优化方案：**

| 层面 | 问题 | 方案 | 效果 |
|------|------|------|------|
| 渲染层 | 全量 re-render | 节点虚拟化 + React.memo + 精确 props 比较 | 渲染节点从 500 降到 30（视口内） |
| 计算层 | 连线路径同步计算 | 移到 Web Worker 异步计算 | 主线程释放 60% |
| 状态层 | 拖拽高频 setState | requestAnimationFrame 节流 + 批量更新 | setState 频率从 60/s 降到 30/s |
| 内存层 | SVG 对象泄漏 | 连线节点销毁时清理 ref 和事件监听 | 内存稳定不增长 |
| 网络层 | 节点配置频繁请求 | 请求去重 + Redis 缓存 | 请求量减少 70% |

**结果：** FPS 从 15 提升到 50+，拖拽延迟从 200ms 降到 30ms。

### Q24. Google 广告及归因系统 API 调研对接，你怎么做的？

   - 权限范围：只申请必要 scope（`ads.readonly`）

4. **数据展示**
   - ECharts 可视化广告投放效果（花费、曝光、点击、转化）
   - 归因数据多维度对比（渠道/时间/地域）

### Q25. 鸿蒙开发跟普通前端开发有什么区别？

**最优回答思路：**

**开发框架差异：**

| 维度 | Web 前端 | 鸿蒙 (ArkTS/ArkUI) |
|------|----------|---------------------|
| 语言 | JavaScript/TypeScript | ArkTS（TS 超集） |
| UI 框架 | React/Vue | ArkUI（声明式 UI） |
| 布局 | CSS Flex/Grid | Flex/Column/Row 声明式 |
| 状态管理 | useState/Pinia | @State/@Prop/@Link 装饰器 |
| 事件 | addEventListener | onClick/onTouch |
| 生命周期 | useEffect/onMounted | aboutToAppear/aboutToDisappear |

**核心区别：**
1. **ArkTS 是 TS 超集**：类型系统更严格，禁用 `any`、`unknown`，编译时静态检查
2. **ArkUI 声明式**：类似 SwiftUI / Flutter，不是 DOM 操作
3. **状态驱动 UI**：`@State` 变量变化自动触发 UI 更新，类似 Vue 的响应式
4. **分布式能力**：鸿蒙原生支持跨设备调用（手机 → 平板 → 智慧屏），前端没有对应概念
5. **性能**：ArkTS 编译为方舟字节码，接近原生性能，比 WebView 快

## 附：高频追问快答速查

| 问题 | 核心要点 |
|------|---------|
| Virtual DOM 一定比真实 DOM 快吗？ | 不一定。Virtual DOM 的优势是跨平台和声明式编程，直接操作 DOM 在精确更新时更快 |
| Vue 的 `nextTick` 原理？ | 利用微任务（Promise.then）在 DOM 更新后执行回调 |
| React Fiber 解决了什么问题？ | 解决旧架构同步递归 Diff 不可中断导致主线程阻塞的问题，支持时间切片 |
| qiankun 的 JS 沙箱怎么实现？ | Proxy 代理 window 对象，子应用对 window 的操作被拦截隔离 |
| Docker 多阶段构建好处？ | 最终镜像不含构建工具和源码，体积小、安全、启动快 |
| LangGraph 的 checkpoint 是什么？ | 工作流状态持久化，中断后可从最近 checkpoint 恢复执行 |
| Redis 缓存大模型请求的意义？ | 相同 prompt 不重复调用模型，降低延迟和 API 成本 |
| NestJS 的依赖注入怎么理解？ | IoC 容器管理对象创建和注入，组件只需声明依赖，不需要手动 new |
| 前端微服务和微前端区别？ | 微服务是后端服务拆分，微前端是前端应用拆分，关注点不同 |
| 大模型 token 消耗怎么控制？ | 缓存相似请求、截断历史对话、用更小的模型处理简单任务 |
