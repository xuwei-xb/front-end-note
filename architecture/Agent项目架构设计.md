# Agent 项目架构设计（设计思路与方案）

> 面向工程落地：从「要不要上 Agent」到分层架构、编排、工具、记忆、前端、部署与安全的完整决策链。
> 与 [[interview/许威面试题汇总-前后端AI]] 的 AI 问答互补：那边是「怎么答」，这边是「怎么设计」。

---

## 〇、结论先行

**Agent 项目 = 一个带状态的循环执行器 + 一组被标准化描述的能力 + 可中断可恢复的运行时。**

三条不可退让的设计原则：

| 原则 | 含义 | 违反的代价 |
|------|------|-----------|
| **能用 Workflow 就别上 Agent** | 流程可预先枚举 → 确定性代码；只在必须"多轮与环境交互 + 路径不可预知"时才交给 LLM 决策 | Token 成本 4–8x、结果不可复现、评测困难 |
| **工具接口先标准化，再谈编排** | Tool 的 name / description / JSON Schema 是契约；描述质量决定 Agent 上限 | 模型选错工具、参数幻觉、调试靠猜 |
| **状态从第一天就要可持久化** | 图状态外置（checkpoint + thread_id），运行时无状态 | 无法断点续跑、无法人工介入、无法多实例横向扩展 |

架构分层总览（六层，自下而上依赖）：

```
接入层   Web/App · 画布编排 UI · 网关(鉴权/限流/流式转发)
─────────────────────────────────────────────
编排层   Graph / State Machine · 路由 · 循环 · 中断恢复   ← 核心
─────────────────────────────────────────────
能力层   Tools(MCP) · Skill · 子 Agent · 外部 API
─────────────────────────────────────────────
上下文层 System Prompt · 会话记忆 · 长期记忆 · RAG 检索
─────────────────────────────────────────────
模型层   模型路由 · 结构化输出 · 重试降级 · 多供应商
─────────────────────────────────────────────
观测层   Trace · Eval · Token/成本 · 失败率告警
```

## 一、第一步：判型（Workflow / Agent / 混合）

**先判型，再谈架构。** 判型错了，后面做得再精致都是过度设计。

| 判据 | 偏向 Workflow | 偏向 Agent |
|------|--------------|-----------|
| 步骤能否预先枚举 | 能，且步骤稳定 | 不能，路径取决于中间结果 |
| 是否需要多轮与环境交互 | 一次调用即可 | 需要反复试错/检索/调用 |
| 失败成本 | 高（不能乱来） | 可容忍（错了重试即可） |
| 输出确定性要求 | 强（结构化、可审计） | 弱（自然语言可接受） |
| Token 预算 | 敏感 | 不敏感 |

**生产形态基本都是混合**：外层 Workflow 定骨架（阶段流转、审批卡点），内层某几个阶段嵌 Agent 做探索（信息补全、异常处理）。

四种 Agent 工作模式的选型（与面试篇 Q27 一致）：

| 模式 | 适用 | 代价 |
|------|------|------|
| ReAct | 通用、边想边做 | Token 高、可能绕路 |
| Plan-and-Execute | 步骤多且可前置规划 | 计划错则全错，需重规划机制 |
| Reflection | 质量优先的产出（代码/文案） | 迭代轮次翻倍 |
| Multi-Agent | 角色差异明显（研究员/审查员/执行者） | 最贵，通信成本高，调试最难 |

> 反模式：一上来就 Multi-Agent。多数场景单 Agent + 好工具 + 好 Prompt 已足够；角色分工能用「一个图里不同节点不同 systemPrompt」解决，不必拆多个模型实例。

## 二、编排层设计（架构的核心）

### 2.1 为什么用图而不是链

链（Chain）是静态线性执行，一次跑完；Agent 需要 **循环（思考→行动→观察）+ 条件分支 + 可中断 + 可恢复**，天然是一张**有向图**。

| 能力 | Chain | Graph |
|------|-------|-------|
| 条件分支 / 循环 | ✗ | ✓ |
| 跨步状态流转 | 手动拼接 | 全局 State + reducer |
| 断点续跑 | ✗ | ✓（checkpoint） |
| 人工介入 | 硬编码 | ✓（interrupt / resume） |
| 节点级流式 | 难 | ✓ |

### 2.2 State 设计三条规则

1. **单一数据源**：所有节点只读写 State，不靠闭包/全局变量传递。
2. **字段必须配 reducer**：并行节点会同时写同一字段，没有 reducer 会**覆盖丢数据**（列表类必须用追加语义）。
3. **不塞全量上下文**：State 存「结构化结论 + 引用」，原文放记忆/检索层按需取，否则每轮都在为垃圾 token 付费。

典型 State 字段：`messages`(追加) · `plan`(覆盖) · `toolResults`(追加) · `intent`(覆盖) · `retryCount`(累加) · `artifacts`(追加)。

### 2.3 循环与终止（必须显式设计）

| 机制 | 作用 |
|------|------|
| 最大步数 / `recursionLimit` | 硬上限，超限抛错并降级为「抱歉没能完成 + 已获得的部分结果」 |
| 重复检测 | 相同工具 + 相同参数连续出现 N 次 → 强制跳出 |
| 超时控制 | 整图超时 + 单节点超时，避免长尾拖死连接 |
| 预算熔断 | Token/费用上限，触顶提前终止 |

### 2.4 中断与人机协同（Human-in-the-loop）

- **哪些节点该中断**：写操作（下单/发信/改数据）、不可逆操作、金额/权限相关、模型置信度低。
- **机制**：节点内触发中断 → 状态持久化 → 前端弹确认卡 → 用户确认后携带状态恢复执行。
- **价值**：既是安全闸门，也是唯一能在生产环境"兜住"模型幻觉的手段。

## 三、能力层设计（工具 / Skill / 子 Agent）

### 3.1 工具即接口契约

一个合格的 Tool 定义包含：**唯一名称 + 说清"何时用/不用"的描述 + 严格 JSON Schema 参数 + 明确的错误语义**。

- **粒度**：一个工具只做一件事。`searchDocs` 优于 `doEverything`；参数越少越准。
- **描述比实现更重要**：模型只看得到 description，描述里要写触发场景与边界（"仅当用户提供订单号时使用"）。
- **返回值要瘦身**：长文本先截断/摘要再回灌，避免把上下文一次烧光。
- **错误隔离**：工具失败必须被节点捕获、转成结构化错误回灌给模型，**不能让异常炸穿整图**。
- **幂等与重试**：读操作可自动重试；写操作必须带幂等键，重试前先查状态。

### 3.2 工具接入的三条路线

| 路线 | 说明 | 适用 |
|------|------|------|
| 内置函数（Function Calling） | 代码内直接注册，最轻 | 项目私有工具、数量少 |
| MCP | 开放协议（Host→Client→Server，JSON-RPC 2.0；原语 Tools/Resources/Prompts），工具实现一次、所有兼容 Agent 复用 | 需要跨 Agent/跨团队复用 |
| Skill | 提示词与流程的工程化封装（元数据常驻 + 主体按需加载） | 沉淀"怎么做"的方法论 |

一句话分层：**Agent 是"谁来做"（决策），Skill 是"怎么做"（方法论），MCP 是"用什么做"（工具连接）。** MCP 不取代 Function Calling，它是 FC 之上的生态标准层。

### 3.3 权限分级（安全的第一道闸）

| 级别 | 行为 | 例 |
|------|------|-----|
| L0 只读 | 自动执行 | 查询、检索、算数 |
| L1 受限写 | 自动执行 + 审计日志 | 写草稿、更新自己的数据 |
| L2 敏感写 | 强制人工确认 | 支付、发通知、改权限 |
| L3 危险 | 默认禁用，白名单 | 删数据、执行任意代码 |

### 3.4 子 Agent

当一个节点需要"独立的上下文 + 独立的工具集 + 独立的输出契约"时，才拆成子 Agent（如 检索员 / 审查员）。否则用同一图内的不同节点即可——**拆子 Agent 的成本是上下文割裂与信息传递损耗**。

## 四、上下文与记忆层

### 4.1 四层记忆

| 层 | 内容 | 生命周期 | 实现 |
|----|------|---------|------|
| 系统层 | 角色、规则、输出格式、安全约束 | 常驻 | System Prompt（含分隔符隔离用户输入） |
| 会话层 | 当前 thread 的对话与中间结果 | 单次会话 | State + checkpoint |
| 长期层 | 用户偏好、历史事实 | 跨会话 | 结构化表（用户画像）+ 向量库（语义检索） |
| 检索层 | 外部知识（文档/知识库） | 按需 | RAG：切分 → Embedding → Top-K → Rerank → 拼 Prompt |

### 4.2 上下文预算

把窗口当预算分配，而不是"塞满为止"：

```
System 规则  ~10%
长期记忆召回 ~15%
检索上下文   ~35%
对话历史     ~25%
留给输出     ~15%
```

压缩手段：滑动窗口 → 摘要历史 → 按需召回（不常驻）。**优先降级顺序：先砍检索冗余，再压历史，最后才动 System 规则。**

## 五、模型层

- **分级路由**：意图分类/打分/摘要用小模型；复杂推理、规划、工具选择用大模型。成本常能降 50%+。
- **结构化输出**：能用 JSON Schema 约束就别用自然语言解析。工具调用、路由判断、字段抽取全部走 schema。
- **可靠性**：超时重试（指数退避）、供应商降级、限流排队、单请求预算上限。
- **抽象一层**：把模型客户端封成统一接口（`chat(messages, tools, stream)`），便于换模型、A/B 与降级。不要在图节点里直接硬编码某家 SDK。

## 六、接入层与前端设计

前端在 Agent 项目里不是"壳"，而是**运行时的一部分**（执行可视化 + 人工介入入口）。

### 6.1 流式接收

| 方式 | 特点 | 选型 |
|------|------|------|
| `EventSource` | 原生、自动重连，但只支持 GET、单向 | 服务端单向推送 |
| `fetch` + `ReadableStream` | 支持 POST、可自定义 header，需手写 `data:` 解析 | **LLM 对话流式（推荐）** |
| WebSocket | 双向 | 协同编辑、双向实时 |

渲染性能（长会话必踩）：
- chunk 存 `useRef`，用 `requestAnimationFrame` 批量 flush 到 state，避免每 token 一次 re-render。
- 流式 Markdown 要处理**未闭合结构**（代码块围栏未闭合先不渲染）。
- 消息列表虚拟化，自动滚动用「是否在底部」判断，避免打断用户翻阅。

### 6.2 执行可视化（Agent 产品的差异化）

- **时间线**：每一步（Thought / Tool Call / Observation / Token 用量 / 耗时）可展开。
- **图状态高亮**：当前节点、已走过的路径、跳过的分支。
- **引用溯源**：RAG 结果标注来源，可点击回原文。

### 6.3 画布编排（配置化）

前端可视化配置 → 序列化为 **JSON Schema** → 后端动态建图执行：

`ReactFlow 拖节点（Agent/工具/条件）` → `属性面板配 model/systemPrompt/tools` → `条件边写表达式` → `导出 Graph Schema` → `后端建图` → `执行状态回推高亮`

约束：Schema 必须**版本化**（图结构变更要能回滚）；节点/边的类型定义放 shared 包，前后端共用一份 TS 类型。

### 6.4 会话管理

`thread_id` 是会话与状态恢复的钥匙——前端切会话就是换 thread_id，后端据此加载 checkpoint 继续跑。

## 七、后端与部署

| 关注点 | 方案 |
|--------|------|
| 无状态 API | HTTP 层不持有会话状态，全部落 checkpoint |
| 有状态运行时 | 状态存 Redis（快、热数据）/ Postgres（可审计、可查询）/ 内存（仅开发） |
| 流式网关 | Node 侧统一流式出口（如 `@Sse()`），处理背压与断连清理 |
| 并发隔离 | 按 `thread_id` + 租户隔离；同 thread 串行、跨 thread 并行 |
| 长任务 | 超过网关超时的执行转任务队列，前端轮询/订阅进度 |
| 热插拔 | 能力以插件形式注册（底座 + 插槽 + 插头）：新增业务只写适配插槽的能力包，不动底座 |

## 八、观测与评测（最容易被跳过的部分）

- **Trace**：每次执行记录完整的节点序列、工具调用参数与返回值、token 与耗时——出问题能一眼定位是"模型选错工具"还是"工具返回脏数据"。
- **Eval**：建固定用例集（含边界与对抗样本），改动 Prompt/工具后跑回归。指标：任务成功率、工具选择准确率、平均步数、单次成本、P95 延迟。
- **成本看板**：按会话/用户/版本拆分 token 消耗，异常自动告警。
- **失败归因分类**：规划错 / 工具错 / 参数错 / 上下文缺失 / 超时——不同归因对应不同修法。

**没有 Eval 的 Agent 项目 = 不可维护。** 每次改 Prompt 都是在赌。

## 九、安全与合规

| 风险 | 对策 |
|------|------|
| Prompt 注入 | 用户输入与系统指令用分隔符/结构化字段隔离；输入侧检测可疑指令；对"读到的内容"不当作指令执行 |
| 越权调用 | 工具权限分级 + 最小权限（scope 收紧）+ 敏感操作二次确认 |
| 数据泄露 | 输出侧过滤敏感字段；日志脱敏；检索层做文档级权限过滤（用户问不到他没权限的文档） |
| 沙箱 | 代码执行/文件操作走沙箱容器，限网络、限资源、限时长 |
| 审计 | 每次工具调用落审计日志（谁、何时、什么参数、结果如何） |

## 十、工程落地顺序（最小可用路径）

| 阶段 | 目标 | 内容 | 不做什么 |
|------|------|------|---------|
| **P0 MVP** | 跑通闭环 | 单 Agent + 3–5 个工具 + 内存 checkpoint + 流式输出 + 最简前端 | 不做多 Agent、不做画布、不做长期记忆 |
| **P1 可用** | 能给人用 | Redis checkpoint + 工具权限分级 + Trace + 20 条 Eval 用例 + 会话管理 | 不做多租户、不做复杂 RAG |
| **P2 增强** | 提效果 | RAG 检索 + Rerank + 长期记忆 + 模型分级路由 + 人工确认节点 | 不急着做 Multi-Agent |
| **P3 规模化** | 能上生产 | 多租户隔离 + 任务队列 + 成本看板 + 告警 + 灰度与版本回滚 + 画布配置化 | — |

**每一阶段都必须有可量化的验收指标**（成功率/延迟/成本），否则无法判断是否该进入下一阶段。

## 十一、项目骨架参考

```
src/
  graph/            # 编排层：图定义、边与路由条件
  nodes/            # 节点实现：thinking / tool / reflect / human / finalize
  tools/            # 能力层：每个工具一个文件 + 注册表（含权限级别标记）
  mcp/              # MCP client 与外部 server 接入
  memory/           # 上下文层：短期压缩、长期记忆读写、RAG 检索
  model/            # 模型层：统一客户端、路由、重试降级、结构化输出
  runtime/          # 有状态运行时：checkpoint 存取、并发/租户隔离、中断恢复
  server/           # 接入层：鉴权、限流、流式接口、任务队列
  observability/    # trace 埋点、token 计量、eval 用例与跑批
  shared/           # 前后端共享的类型与 Graph Schema 定义（单一事实来源）
web/
  chat/             # 对话：流式渲染、时间线、引用溯源、确认卡片
  flow/             # 画布：拖拽编排、属性面板、Schema 导入导出
  sessions/         # 会话列表与 thread_id 管理
```

> 骨架的判据很简单：**任何一个你将来会想替换的东西（模型、状态存储、检索库、前端框架），都应该有独立目录且只通过接口被依赖。**

## 十二、反模式清单（踩过就别再踩）

1. 用 Agent 做本该用 if/else 的确定性流程。
2. State 字段不配 reducer，并行节点悄悄丢数据。
3. 工具描述含糊（"处理数据"），模型只能靠猜。
4. 工具返回超长原文直接回灌，一轮烧光上下文。
5. 没有最大步数 / 超时 / 预算熔断，线上出现无限循环刷 token。
6. 图状态只存内存，服务重启后所有会话失效。
7. 没有 Trace，出问题只能靠复现和猜。
8. 没有 Eval 就反复调 Prompt，效果"感觉变好了"。
9. 前端每个 token 触发一次 re-render，长会话直接卡死。
10. 敏感工具无人工确认，一次幻觉造成不可逆损失。

## 十三、同一矛盾，不同支柱（跨案例同构）

> 视角提炼：拆 WorkBuddy / LangGraph / OPC 三个系统，底层是同一副骨架——**凡是"裸 X"，本质都在补「状态 + 控制 + 持久化」三件套，把不可控的线性执行体变成可控的有状态系统。** 区别只在场景，支柱落点不同。

| 裸执行体 | 要补的矛盾 | 支柱三件套 |
| --- | --- | --- |
| 裸模型（WorkBuddy 宿主） | 无状态/不可控/不可观 ⇄ 稳定、个性化、可追责的产品 | 记忆 + 约束 + 观测 |
| 裸链（LangGraph） | 无状态/无循环/无暂停 ⇄ 可控、有状态、可暂停的执行流 | State + 图 + Checkpoint + interrupt |
| 裸接入（OPC） | 异构业务 ⇄ 多变 AI ⇄ 标准适配层 | 底座 + 插槽 + 插头 |

- 同构但分形：同样的"无状态"矛盾，WorkBuddy 用**记忆文件层**（跨会话个性），LangGraph 用 **State+Checkpoint**（单次执行中间态）——同一矛盾、不同支柱，正是架构取舍要盯的点。
- 呼应：本笔记第八节（观测 = 可追责的"持久化/可归因"一半）、第三节（权限分级 = 约束的执行侧）。
- 用法：下次看任何 Agent 平台/框架，先问——它给"裸执行体"补了哪三样？能答出，就看清了设计主线。
