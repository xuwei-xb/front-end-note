# Agent 宿主平台设计剖析（以 WorkBuddy 为例）

> 拿一个真实产品化的 Agent Host 当标本，对照 [[architecture/Agent项目架构设计]] 的六层方法论，反推"大脑该怎么搭"。
> 价值：把抽象方法论落到可观察的实现上，建立"看到一个 Agent 产品就能拆出架构"的直觉。

---

## 〇、为什么拿 WorkBuddy 当标本

它是**完整产品**而非 demo：接入层、编排、能力生态、记忆、多模态、安全、可视化全都在场，且能从它暴露的能力（200+ 工具、Skill、Connector、Memory、子 Agent）反向推出设计意图。对照 [[architecture/Agent项目架构设计]] 的六层，几乎每层都有落点。

---

## 一、接入层：自然语言是第一公民，但一切皆工具

| 设计点 | WorkBuddy 实例 | 给大脑的启发 |
|--------|---------------|-------------|
| 入口统一 | 单一对话入口，所有能力通过"调用工具"完成 | 宿主不堆功能页，而是堆**可调用单元** |
| 工具护栏 | `tool_use` 政策：优先专用工具、可并行、禁止占位符、专用 agent 优先 | 能力多了必须靠**调用纪律**约束，否则模型乱选 |
| 模式切换 | Agent / Plan / Ask 三种 mode | 把"自主权 vs 可控"做成显式开关，而非写死 |

**启发**：宿主的核心价值 = 把"能力"做成可插拔单元 + 一套调用纪律。能力越多，护栏越重要。

---

## 二、编排层：主脑循环 + 按需派单，而非一上来 Multi-Agent

| 设计点 | WorkBuddy 实例 |
|--------|---------------|
| 主循环 | 感知→规划→行动→记忆 的 agent loop，自带上下文窗口管理 |
| 派单 | 复杂/独立任务派给 `Explore`（探查）/ `Plan`（只读规划）/ `general-purpose`（执行）子 Agent |
| 任务清单 | `TaskCreate/Update/List` 把多步任务显式建模，避免模型脑内记账 |

**启发**：真实产品很少"启动就多智能体对喷"，而是**单主脑循环 + 按任务类型派单**——既保自主性，又把"重型独立任务"隔离出去互不污染上下文。这正对应方法论「子 Agent 拆分时机」那一节。

---

## 三、能力层：Skill（怎么做）与 Connector（用什么做）分离

| 概念 | 设计落点 | 说明 |
|------|---------|------|
| **Skill** | 100+ 内置/可装技能，三级结构（metadata 常驻 + core 按需 + references 按需） | 方法论封装，**按需加载**避免 context 浪费 |
| **Connector** | `recommend-connectors`、`search_plugins`，MCP Server 接入 | 外部能力接入标准化（工具/服务/API） |
| **Expert** | 专家 / 专家团队，多角色协作 | 角色化 Prompt 包，等价于"垂直领域子 Agent" |

**启发**：再次印证三元分层——**Agent 是"谁来做"（决策），Skill 是"怎么做"（方法论），Connector 是"用什么做"（连接）**。把方法论和连接拆开，是降低上下文成本的关键设计。

---

## 四、上下文与记忆：三层 + 显式写入

| 层 | WorkBuddy 实现 | 生命周期 |
|----|---------------|---------|
| 云档案（只读） | 服务端生成的用户画像，session 注入 | 跨会话、不可本地改 |
| 用户级本地记忆 | `~/.workbuddy/MEMORY.md` | 跨项目长期偏好 |
| 工作区级记忆 | `项目/.workbuddy/memory/` 日志 + MEMORY.md | 项目内长期 |
| 会话上下文 | agent loop 的实时上下文 | 单次 |

**启发**：记忆不是"自动发生"的，而是**显式动作**（写文件/更新）。且与会话上下文解耦——长期事实走结构化文件，会话只带结论。这对应方法论「四层记忆 + 不塞全量上下文」。

---

## 五、模型层：分级路由是默认，不是优化项

- 主模型跑 agent loop；子 Agent 可按任务选 `lite`（快/省）或 `reasoning`（强推理）。
- 多模态生成（图/视频/3D）走专用模型，与文本 LLM 解耦。
- 系统环境走 **managed runtime 隔离**（Python/Node 沙箱），不污染用户环境。

**启发**：分级路由、专用模型、运行隔离，在成熟产品里是**基座设计**，不是后期优化。方法论第五节讲"模型层"时要把它当必选项。

---

## 六、观测与安全：护栏前置成架构约束

| 维度 | 落点 |
|------|------|
| 内容护栏 | content_policy 前置拦截（政治/隐私/敏感） |
| 权限最小化 | 沙箱执行、runtime 隔离、危险操作需用户确认 |
| 主题适配 | 视觉输出随 IDE 主题（light/dark）切换——把"可观测/可呈现"纳入体验 |

**启发**：安全是**架构约束**不是补丁。敏感操作的人机协同（interrupt）在宿主层就内建了，印证方法论第九节。

---

## 七、给"大脑思路搭建"的三条核心结论

1. **宿主 = 编排 + 生态**。自研能力越少、接入生态越标准，平台越值钱（Skill/Connector/MCP）。
2. **上下文工程是护城河**。同一个模型，system/memory/工具描述怎么组织，决定 Agent 上限。WorkBuddy 的 Skill 三级加载、记忆分层、调用纪律，本质都在做这件事。
3. **渐进派单而非多智能体**。主脑循环 + 按任务派子 Agent，是工程上最稳的解法。

> 这三条反过来就是设计 Agent 大脑时的**检查清单**：你今天的编排是单主脑还是乱开多体？你的能力是 Skill/Connector 分离了吗？你的上下文分层了吗？

---

## 八、对照方法论的反查表

| 方法论层（[[architecture/Agent项目架构设计]]） | WorkBuddy 落点 | 面试能怎么讲 |
|------|------|------|
| 判型 | 默认单主脑 + 按需派子 Agent | "我们不是一上来多 Agent，而是主循环 + 任务派单" |
| 编排层 | agent loop + Task 清单 + mode 切换 | "多步任务用显式任务清单建模，不让模型脑内记账" |
| 能力层 | Skill + Connector + Expert | "方法论和连接拆开，按需加载控 context" |
| 上下文/记忆 | 三层记忆 + 显式写入 | "长期事实走文件，会话只带结论" |
| 模型层 | 分级路由 + 专用模型 + 沙箱 | "路由/隔离是基座设计不是优化" |
| 观测/安全 | 护栏前置 + 最小权限 | "安全是架构约束，敏感操作内建确认" |
